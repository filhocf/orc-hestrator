# Identity and presence

## The triple

Every session is identified by `hostname / agent_id / session_id`:

- `hostname` — from the `agent_register` argument, else the `X-Client-Hostname`
  header, else `unknown`.
- `agent_id` — resolved **per request** from, in order: a tool argument → the
  `X-Agent-ID` header → the `MCP_AGENT_ID` env var → the OAuth client id. Never
  cached across requests.
- `session_id` — generated by `agent_register` and returned to you. **Reuse it**
  on every subsequent call in the session.

Without an `agent_id`, writes are recorded with a null author. If you want the
board to show *who* did what, set `X-Agent-ID` (header) or `MCP_AGENT_ID` (env).

## Lifecycle

```
agent_register(cli="...", hostname="...")   → session_id
agent_heartbeat(session_id)                  every 2-3 minutes
agent_end(session_id)                         on exit (releases claims, CASCADE)
```

Sessions with no heartbeat for more than 300 seconds are reaped centrally. A
reaped session loses its claims, so another agent could take the work — heartbeat
if you intend to hold an item across a long operation.

## Seeing the team

`agent_list()` lists active sessions across all machines, optionally filtered by
`hostname` or `agent_id`. It lazily reaps stale sessions first, so the list
reflects live presence.

## Two audiences, two auth paths

- **Humans** use cookie sessions with RBAC on the REST `/api/*` surface (the web UI).
- **Agents** use the reverse proxy's basic auth and, optionally, OAuth2
  (`MCP_OAUTH_ENABLED`). The `agent_id` for attribution rides the `X-Agent-ID`
  header regardless of which auth is in front.
